# Удаление и архив мастеров и услуг

Изменения подготовлены локально 29 октября 2026 года. Облачная база не изменялась.

## Применение к существующему Supabase

После уже применённых миграций `001`–`006` выполните в SQL Editor Supabase **по очереди** содержимое файлов:

1. `supabase/migrations/202610290007_active_media_admin.sql` — сохраняет ручное исправление `private.assert_media_admin(uuid)`: проверяется `user_id` **и `active = true`**. `CREATE OR REPLACE` совместим с уже исправленной вручную функцией; назначения администраторов не меняются.
2. `supabase/migrations/202610290008_catalog_archive.sql` — добавляет архив, защищённые операции и фильтрацию публичного каталога/доступности записи.

Если миграции ведутся через CLI, используйте эти же два новых файла в обычном процессе миграций проекта. Не выполняйте повторно старые миграции, `seed.sql` или `db reset`. Каждый новый файл содержит свою транзакцию.

После применения обновите фронтенд обычным способом (`npm.cmd run build`). До применения миграций новые кнопки не смогут выполнить операции. Новых Edge Functions, ключей и настроек Storage для этой доработки нет. Существующие `booking-gateway`, `site-media` и плановая очистка из [MEDIA_SETUP.md](MEDIA_SETUP.md) остаются нужны; их код и настройки не менялись.

## Интерфейс

- `/admin` → «Мастера»: «Удалить» в карточке под «Профиль и график».
- `/admin` → «Услуги»: «Удалить» в строке рядом с редактированием.
- В обоих разделах доступны «Текущие» / «Архив». В архиве — «Восстановить» с подтверждением.
- Нажатие «Удалить» сначала запрашивает актуальную проверку сервера. При отсутствии любых записей можно подтвердить полное удаление либо выбрать «В архив». Если есть история (включая отменённые записи), предлагается только архив.
- Если есть будущие или ещё идущие неотменённые визиты, отображается их количество. Сначала перенесите или отмените их в разделе «Записи». Автоматической отмены нет. Проверка учитывает все статусы кроме `cancelled`, даже если будущему визиту ошибочно присвоен статус завершённого/неявки.
- Восстановление сохраняет прежнюю активность услуги. Если услуга была скрыта до архива, включите её активность отдельно. Архивные назначения услуг у мастера сохраняются, но новые бронирования по ним запрещены.
- Полное удаление архивного объекта без истории возможно после его восстановления.

## Сохранность и права

`admin_catalog_impact` используется для подтверждения; `admin_catalog_action` повторяет проверку внутри транзакции. Удаление/архивирование берёт ту же `private.lock_salon()`, что создание, перенос и изменение статуса записи, затем существующую блокировку медиа. Проверка общей ревизии не позволяет применить устаревшее подтверждение. Администратор проверяется сервером через активную запись `private.admin_users`; браузерные роли не используются.

`private.slot_available` запрещает архивные услуги и мастеров для создания, переноса и восстановления отменённой записи. Это распространяется на прямой административный RPC и служебный вход `booking_gateway_execute` для гостевого Edge gateway. Публичный каталог исключает архив; административный снимок сохраняет все объекты. В клиентской истории сохраняется имя архивного мастера.

Архив не удаляет записи, коды управления, уведомления, настройки, фотографии и привязки. Полное удаление мастера без записей удаляет только его привязки услуг и блокировки времени через существующие внешние ключи. Удаление услуги убирает её привязки у мастеров. Внешние ключи записей остаются `ON DELETE RESTRICT`.

Файлы фотографий не удаляются операцией каталога. Используется существующая очистка `site-media`: все ссылки, включая архивных мастеров и общие изображения, защищены; бесхозные файлы старше 24 часов подхватываются при очистке. Ошибка фоновой очистки не откатывает успешное удаление объекта; следующий плановый запуск повторит её.

## Локальная проверка и границы

Тесты SQL выполняются в изолированной PGlite с миграциями, ролями и правами. Браузерные тесты используют Chrome и HTTP-адаптер Supabase на localhost; название команды `test:cloud` не означает подключение к облаку. Покрыты удаление без записей, зависимости, история, отменённые и текущие визиты, восстановление, запреты прямых операций бронирования, устаревшая ревизия, неактивный администратор и общие фотографии. Отдельно проверено применение новых миграций поверх базы `001`–`006` с существующей записью и фото.

На настоящем Supabase после ручного применения проверьте вход активного администратора, отказ обычному/отключённому пользователю, обновление каталога в другом браузере и одновременные запросы из двух независимых соединений PostgreSQL. Локальная PGlite не моделирует реальную конкуренцию нескольких серверных соединений: локально проверены оба порядка операций и повторная проверка после появления новой записи. Настоящие облачные Auth/Storage и устройства не использовались.
