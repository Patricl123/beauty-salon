# Подключение AURA к Supabase / PostgreSQL

**Если Supabase уже подключён:** первоначальные шаги ниже повторять не нужно. Для установки Turnstile и лимитов используйте [PROTECTION_SETUP.md](PROTECTION_SETUP.md): применяется только новая миграция `202610270005_booking_protection.sql` и развёртывается `booking-gateway`, без сброса данных.

Дизайн и маршруты сохранены. Подготовлены два изолированных режима:

- Без настроек окружения — прежняя явно обозначенная **демоверсия** с localStorage.
- `VITE_DATA_SOURCE=supabase` — каталог и записи из PostgreSQL, серверная валидация, Supabase Auth и права доступа. При неверной или неполной конфигурации запуск останавливается: автоматического переключения на демоданные нет.

Ниже описано первоначальное подключение нового проекта. Для уже подключённого проекта переходите к инструкции обновления выше. Не присылайте пароли или ключи в чат.

## 1. Создайте отдельный проект Supabase

1. Откройте [Supabase Dashboard](https://supabase.com/dashboard).
2. Нажмите **New project**, выберите организацию и укажите имя, например `aura-beauty`.
3. Создайте надёжный **Database password**, сохраните его в менеджере паролей. В приложение этот пароль не нужен.
4. Выберите подходящий регион и нажмите **Create new project**. Дождитесь готовности базы.

Миграции рассчитаны на новый проект. Если в вашем Supabase уже есть рабочие таблицы с такими же именами, сначала используйте отдельный тестовый проект: не запускайте SQL поверх существующих данных вслепую.

## 2. Закройте самостоятельную регистрацию

В проекте откройте **Authentication → Sign In / Providers**:

1. В настройках регистрации выключите **Allow new users to sign up** и сохраните изменение.
2. Оставьте **Allow anonymous sign-ins** выключенным.
3. Оставьте включённым вход по **Email / Password**. Не включайте ненужные OAuth-провайдеры.
4. В **Authentication → URL Configuration** задайте **Site URL**: `http://127.0.0.1:5173`. После размещения замените его настоящим HTTPS-адресом сайта.

Клиенты салона не регистрируются в Auth: публичная запись использует персональный случайный код управления. Учётные записи Auth нужны персоналу. Настройки `enable_signup = false` в `supabase/config.toml` относятся к локальному Supabase CLI; облачный переключатель нужно выключить отдельно в Dashboard. [Настройки регистрации Supabase](https://supabase.com/docs/guides/auth/general-configuration).

## 3. Примените SQL-миграции

Откройте **SQL Editor → New query**. Вставляйте **полное содержимое одного файла**, нажимайте **Run** и дожидайтесь успешного выполнения перед следующим:

1. `supabase/migrations/202610250001_schema.sql`
2. `supabase/migrations/202610250002_read_api.sql`
3. `supabase/migrations/202610250003_booking_commands.sql`
4. `supabase/migrations/202610250004_admin_commands.sql`

Каждый файл выполняется транзакционно. Уже успешно применённые миграции повторно не запускайте. Схема `private` не должна находиться в списке exposed schemas: в **Project Settings → Data API** проверьте, что она не опубликована. Приложение использует только `public` RPC.

Проверка после применения в SQL Editor:

```sql
select public.get_public_catalog();

select conname
from pg_constraint
where conname = 'appointments_no_overlap';

select schemaname, tablename, rowsecurity
from pg_tables
where schemaname in ('public', 'private')
order by schemaname, tablename;
```

`appointments_no_overlap` должен существовать, у созданных таблиц должно быть `rowsecurity = true`. Не добавляйте разрешающие политики `using (true)` для записей и заметок.

Для локальной установки через Supabase CLI предусмотрен `supabase/config.toml`; миграции применяются командой `supabase db reset` **только к локальной одноразовой базе**, поскольку reset удаляет её данные. Для обычного подключения достаточно Dashboard: Docker и CLI не обязательны.

## 4. Создайте первого администратора вручную

1. Откройте **Authentication → Users → Add user → Create new user**.
2. Введите email сотрудника и надёжный уникальный пароль. Если показывается **Auto Confirm User**, включите его только после проверки адреса сотрудника владельцем проекта.
3. Создайте пользователя. Откройте его карточку и скопируйте **User UID**.
4. В **SQL Editor → New query** замените только строку UUID в следующем запросе и нажмите **Run**:

```sql
insert into private.admin_users (user_id, active)
values ('PASTE_USER_UID_HERE'::uuid, true)
on conflict (user_id) do update set active = true;
```

Здесь нужен идентификатор уже созданного пользователя, не пароль. Не редактируйте `auth.users` SQL-запросами ради создания аккаунта. В приложении нет формы регистрации, вызовов `signUp`, `auth.admin.createUser` и доступа к выдаче ролей.

Наличие пользователя в Auth само по себе **не даёт доступ** к панели. Роль проверяется по `private.admin_users`; `user_metadata`, значения localStorage и название email не участвуют в выдаче прав. Даже если кто-то ошибочно включит общий signup в Dashboard, новый пользователь не сможет стать администратором через API.

Отозвать доступ можно в SQL Editor:

```sql
update private.admin_users
set active = false
where user_id = 'PASTE_USER_UID_HERE'::uuid;
```

Следующий запрос к базе уже будет запрещён. Интерфейс перепроверяет роль при фокусе окна и каждые 30 секунд. Пароли передавайте сотрудникам вне репозитория и чата, через защищённый канал. Для приглашений и сброса пароля по email потребуется отдельно настроить SMTP и поток установки нового пароля; текущий вход — по уже назначенным email и паролю. [Управление пользователями Supabase](https://supabase.com/docs/guides/auth/users).

## 5. Подключите приложение без серверных секретов

В корне проекта создайте `.env.local` на основе `.env.example`. Если `.env.local` уже существует, отредактируйте его, не перезаписывая чужие настройки.

```dotenv
VITE_DATA_SOURCE=supabase
VITE_SUPABASE_URL=https://YOUR_PROJECT_REF.supabase.co
VITE_SUPABASE_PUBLISHABLE_KEY=YOUR_PUBLISHABLE_KEY
```

Где взять значения:

1. В Dashboard проекта нажмите **Connect** и скопируйте **Project URL**.
2. Откройте **Project Settings → API Keys → Publishable and secret API keys**. В строке **Publishable key** скопируйте значение с префиксом `sb_publishable_`.
3. Подставьте их локально в `.env.local`, сохраните файл. Перезапустите Vite.

Клиентскому приложению нужен только **publishable key**. Он рассчитан на присутствие в браузере; защиту данных обеспечивают SQL-права, RLS и проверка полномочий в RPC. **Secret key**, legacy **service_role**, JWT secret и Database password не нужны ни в одном клиентском файле. [Типы ключей Supabase](https://supabase.com/docs/guides/getting-started/api-keys).

Любая переменная `VITE_*` потенциально попадает в браузер. Проверка конфигурации до сборки отклоняет `sb_secret_*`, ключи с именами `SECRET`, `SERVICE_ROLE`, `PASSWORD`, `DATABASE_URL` и ключи неподходящего формата, не выводя их значения. `.env*` исключены из Git, разрешён только шаблон `.env.example` без реальных значений. Реальные ключи и пароли в Git добавлять нельзя.

## 6. Заполните каталог

Для рабочего салона после входа в `/admin` заполните **Услуги**, **Мастера**, назначьте мастерам услуги и рабочие дни, затем **Настройки**. Реальные записи из браузерной демоверсии автоматически не импортируются.

Для проверки в **отдельном тестовом проекте** можно выполнить в SQL Editor файл `supabase/seed.sql`. Он добавит 13 примерных услуг и 5 примерных мастеров без клиентов, записей, паролей и аккаунтов. Названия, фотографии и цены остаются иллюстративными: перед рабочим запуском замените их. Seed не запускается автоматически.

## 7. Запустите и проверьте

После первоначальных миграций 001–004 установите защиту по [PROTECTION_SETUP.md](PROTECTION_SETUP.md): текущая версия публичного интерфейса использует Edge Function и Turnstile. Одних четырёх исходных миграций для нового интерфейса уже недостаточно.

Node.js: установленная версия 24.13.0 подходит. В PowerShell из папки проекта:

```powershell
npm.cmd ci
npm.cmd run dev
```

Сайт: `http://127.0.0.1:5173`. Панель: `http://127.0.0.1:5173/admin`.

Проверьте следующий сценарий с тестовыми контактами:

1. В `/admin` видна форма email/пароля, нет кнопки демонстрационного входа. Разрешённый сотрудник входит, обычный пользователь — нет.
2. Создайте запись на сайте. Убедитесь, что она появилась в панели и в **Table Editor → appointments**.
3. Сохраните **код управления** с экрана подтверждения. Он содержит случайный секрет, поэтому не публикуйте его и не передавайте посторонним.
4. В другом приватном окне «Мои записи» не показывает чужие визиты. Введите свой полный код — откроется только ваша запись.
5. Перенесите запись: прежний интервал освободится. Отмените: новый интервал освободится, будущие напоминания будут убраны.
6. Попытайтесь отправить два запроса на один интервал: база должна сохранить один визит. Повтор идентичного запроса с тем же ключом возвращает ту же запись.

В серверном режиме бизнес-данные не записываются в localStorage. Сеанс администратора, коды управления и идентификаторы незавершённых запросов хранятся в **sessionStorage**; персональные данные записей читаются с сервера. Код управления — механизм доступа по секрету, а не подтверждение телефона. После закрытия вкладки для восстановления записи используйте сохранённый код. На сайте нет поиска чужих записей по номеру телефона.

## 8. Автоматические проверки

```powershell
npm.cmd run build
npm.cmd test
npm.cmd run test:e2e
npm.cmd run test:cloud
```

- `test` исполняет миграции в изолированном PostgreSQL/PGlite и проверяет RLS, роли, RPC, цены, согласие, пересечения, версии, повторы и атомарность переноса. Он не подключается к облаку.
- `test:e2e` проверяет прежний деморежим в Chrome: запускает отдельный сервер на порту 5174 с принудительным `VITE_DATA_SOURCE=demo`, не переиспользует рабочий сервер.
- `test:cloud` запускает отдельный сайт на порту 5175 и одноразовый тестовый API на 54329: RPC выполняются в PGlite, Auth-протокол имитируется только для теста. Проверяются форма входа, запрет обычному пользователю, создание/перенос/отмена и повтор после потери HTTP-ответа. Это не заменяет проверку вашего настоящего проекта Supabase.

Для **реальной гонки нескольких соединений PostgreSQL** предусмотрен отдельный скрипт. Нужна **пустая одноразовая база без пользовательских таблиц**, а не рабочий Supabase. Задайте `TEST_DATABASE_URL` в локальном окружении/`.env.local`, не в командной строке и не в `VITE_*`. Затем:

```powershell
$env:AURA_ALLOW_DISPOSABLE_DB_TEST = 'yes'
npm.cmd run test:db:live
Remove-Item Env:AURA_ALLOW_DISPOSABLE_DB_TEST
```

Скрипт отказывается запускаться без явного флага или при наличии таблиц в public/private/auth. Создаёт тестовую схему и оставляет её для осмотра. Проверяет параллельные пересекающиеся записи, повтор создания, гонку переноса с отменой и повтор отмены. Не выводит строку подключения и параметры запросов. Самостоятельно удалять рабочие базы или отключать RLS для теста не нужно.

## Как устроена защита

- `appointments_no_overlap`: PostgreSQL `EXCLUDE USING gist` по мастеру и диапазону `[начало, окончание)` для неотменённых визитов. Соседние интервалы допустимы; пересечения запрещены самой базой, независимо от браузерной проверки. [Ограничения диапазонов PostgreSQL](https://www.postgresql.org/docs/15/rangetypes.html#RANGETYPES-CONSTRAINT).
- Все изменения расписания используют одну транзакционную advisory-блокировку салона: запись не проходит одновременно с блокировкой времени или изменением графика. Для текущего размера салона это простой последовательный порядок мутаций; при масштабировании потребуется разбиение по салонам/мастерам.
- Цена, длительность и название услуги берутся из базы. Переданная браузером стоимость служит только подтверждением показанной цены. Изменённая цена требует повторного подтверждения.
- Идемпотентность хранится в `private.idempotency_requests`: субъект + UUID запроса + хеш полезной нагрузки. Другой payload с тем же ключом отклоняется. Ключ и исходная версия сохраняются на время неопределённого сетевого результата; после успешного ответа запрос завершён.
- `version` записи и `revision` общего снимка защищают от потери чужих изменений при устаревшей форме.
- Роли API не могут непосредственно вставлять/изменять/удалять таблицы. Публичные RPC возвращают только каталог и интервалы; личные данные требуют персонального кода либо допущенного администратора. В базе хранится только SHA-256 хеш кода управления.
- Все `SECURITY DEFINER` имеют фиксированный пустой `search_path`; внутренние функции недоступны API-ролям. Изменения прав администратора разрешены только владельцу проекта через доверенное управление базой. [Безопасность SQL-функций Supabase](https://supabase.com/docs/guides/database/functions).

## Что ещё нужно перед открытием записи реальным клиентам


Доставка SMS/WhatsApp/email, оплата и проверка телефона не подключены. CAPTCHA и серверные квоты подготовлены отдельно: установите их по [PROTECTION_SETUP.md](PROTECTION_SETUP.md). Журнал уведомлений хранит `not_sent`, а не «Отправлено». Для публичного запуска также нужны правила обработки/удаления персональных данных, настоящий каталог и контакты, мониторинг и резервные копии. Не добавляйте внешний сервис аналитики, который собирает содержимое форм или коды управления.

При размещении frontend задайте те же **публичные** переменные окружения в настройках хостинга и пересоберите приложение. Настройте SPA fallback на `index.html` для `/admin` и `/bookings`, используйте HTTPS. База и Supabase Auth остаются на стороне Supabase; отдельный Node.js backend для этих RPC не нужен.
