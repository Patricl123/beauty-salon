# Защита публичной записи: установка без сброса данных

Вы уже подключили Supabase и вручную проверили администратора, создание, перенос и отмену. Повторять первоначальную настройку не нужно. Новая защита подготовлена локально; в облако изменения автоматически не применяются.

**До завершения установки новый публичный интерфейс может показывать недоступность записи.** Он не возвращается к старым незащищённым RPC. Действия назначенного администратора сохраняют прежние RPC с дополнительной проверкой роли. Сайт для клиентов пока не публикуйте.

## Что изменяется

Посетитель отправляет запрос в `booking-gateway`. Функция сначала расходует общую квоту PostgreSQL, затем для **создания** проверяет Turnstile через Cloudflare Siteverify. Проверяются success, точный разрешённый hostname, action `salon_booking` и время challenge. Токены одноразовые; после неудачной попытки форма получает новый токен. Ключ бизнес-запроса остаётся прежним при сетевой неопределённости. [Правила Siteverify](https://developers.cloudflare.com/turnstile/get-started/server-side-validation/).

Чтение по коду, перенос и отмена требуют прежний случайный персональный код и теперь проходят серверные лимиты. Повторная CAPTCHA для этих действий не требуется. Свободные интервалы также читаются через ограничиваемую функцию. Публичный каталог без клиентских данных остаётся доступным через `get_public_catalog`.

Миграция переносит существующую реализацию операций в закрытую схему `private`; публичные имена оставляет только для назначенных администраторов. Обычный Auth-пользователь не получает обход. Старые персональные коды, записи, статусы, цены и назначения администраторов сохраняются.

## 1. Создайте виджет Turnstile

1. Откройте [Cloudflare Dashboard](https://dash.cloudflare.com/) и войдите в свой аккаунт.
2. Откройте **Turnstile → Add widget**.
3. Название: например `AURA local verification`.
4. В **Hostname management** добавьте `localhost` и `127.0.0.1` — без протокола, порта и пути.
5. Выберите режим **Managed**, оставьте **Pre-clearance** выключенным.
6. Нажмите **Create**.
7. Сохраните **Site key** и **Secret key** у себя. Site key нужен браузеру; Secret key — только серверной функции. Не присылайте их в чат.

Для будущего публичного сайта создайте отдельный виджет только с настоящим доменом. Не используйте тестовые «always pass» ключи для рабочего проекта. Наш сервер проверяет action и hostname, а не только success. [Создание виджета](https://developers.cloudflare.com/turnstile/get-started/widget-management/dashboard/), [локальные домены и тестирование](https://developers.cloudflare.com/turnstile/troubleshooting/testing/).

## 2. Внесите публичный ключ локально

Откройте **существующий** корневой `.env.local`. Сохраните текущие настройки Supabase; добавьте только новую строку или отредактируйте её, если она уже есть:

```dotenv
VITE_TURNSTILE_SITE_KEY=ВАШ_SITE_KEY
```

Не копируйте весь `.env.example` поверх существующего файла. Secret key не должен иметь префикс `VITE_`. Проверка конфигурации отклоняет переменные с именами SECRET/SERVICE_ROLE/PASSWORD среди VITE-переменных, не печатая значения.

## 3. Сохраните серверные секреты

В **существующем проекте Supabase → Edge Functions → Secrets** добавьте и сохраните:

| Name | Value для локальной проверки сайта |
| --- | --- |
| `TURNSTILE_SECRET_KEY` | Secret key вашего виджета |
| `TURNSTILE_ALLOWED_HOSTNAMES` | `localhost,127.0.0.1` |
| `BOOKING_ALLOWED_ORIGINS` | `http://localhost:5173,http://127.0.0.1:5173` |

Origin включает протокол и порт, без завершающего слеша. Hostname — без протокола и порта. Неверные или отсутствующие настройки закрывают публичные операции с безопасной ошибкой.

`SUPABASE_URL` и `SUPABASE_SERVICE_ROLE_KEY` функция получает из своего серверного окружения Supabase. Не переносите service_role в браузер и не пытайтесь вручную создать пользовательский секрет с зарезервированным префиксом SUPABASE_. [Секреты Edge Functions](https://supabase.com/docs/guides/functions/secrets).

Если хотите хранить копию настроек для **локального запуска Edge Function**, создайте `supabase/functions/.env` по шаблону `supabase/functions/.env.example`. Это отдельный серверный файл, исключённый из Git. Существующий файл не перезаписывайте. Его наличие само по себе не настраивает облачную функцию — значения нужно сохранить в Dashboard, как выше. Для текущей проверки локального frontend с облачным Supabase локальный серверный файл не обязателен.

## 4. Разверните только серверную функцию

Скопируйте **Project ID / Reference ID** существующего проекта из **Project Settings → General**. Это идентификатор проекта, не пароль.

В PowerShell из папки проекта:

```powershell
npx.cmd supabase@2 login
npx.cmd supabase@2 functions deploy booking-gateway --project-ref YOUR_PROJECT_REF --no-verify-jwt --use-api
```

Замените `YOUR_PROJECT_REF` своим идентификатором. Вход CLI выполните через предложенный браузерный процесс; не добавляйте токен доступа в команды, документацию или Git. `--use-api` позволяет развернуть без локального Docker. Команда развёртывает только Edge Function, не frontend и не миграции. [Развёртывание функций](https://supabase.com/docs/guides/functions/deploy).

В `supabase/config.toml` для этой функции также указан `verify_jwt = false`: посетители не имеют Auth JWT. Защиту обеспечивают серверная CAPTCHA, квоты и персональный код. Функция **не доверяет** роли из Authorization или из тела запроса и всегда выполняет гостевую ветку SQL. Администратор работает отдельно через проверяемые базой RPC. [Конфигурация проверки JWT](https://supabase.com/docs/guides/functions/function-configuration).

В Dashboard проверьте, что **Edge Functions → booking-gateway** появилась. До применения следующей миграции она будет возвращать безопасную ошибку недоступности: нужные серверные RPC ещё не созданы.

## 5. Примените только новую миграцию

Сначала убедитесь, что у проекта есть актуальная резервная копия. Не используйте `db reset`, не выполняйте `seed.sql`, не повторяйте миграции 001–004 и не запускайте `db push` вслепую поверх миграций, ранее применённых через SQL Editor.

1. Откройте **SQL Editor → New query**.
2. Вставьте полное содержимое **`supabase/migrations/202610270005_booking_protection.sql`**.
3. Нажмите **Run** и дождитесь успешного завершения.

Файл выполняется одной транзакцией. Он не удаляет и не перезаписывает клиентские записи. В момент применения старые прямые публичные RPC закрываются; старая открытая вкладка клиента должна быть обновлена. Это намеренная короткая пауза при переключении, а не обход защиты.

Применяйте этот файл один раз. Если SQL Editor сообщил об ошибке, транзакция должна откатиться; изучите причину до повторного запуска. Если применён успешно, не запускайте повторно.

Проверка прав в SQL Editor без просмотра персональных данных:

```sql
select
  has_function_privilege('anon', 'public.create_appointment(uuid,text,jsonb)', 'EXECUTE') as anon_create,
  has_function_privilege('anon', 'public.get_appointment(uuid,text)', 'EXECUTE') as anon_read,
  has_function_privilege('authenticated', 'public.booking_gateway_execute(text,jsonb)', 'EXECUTE') as user_gateway,
  has_function_privilege('service_role', 'public.booking_gateway_execute(text,jsonb)', 'EXECUTE') as server_gateway;
-- Ожидается: false, false, false, true.

select conname from pg_constraint where conname = 'appointments_no_overlap';
-- Ограничение по-прежнему существует.
```

`authenticated` сохраняет EXECUTE на публичные операции, но каждая из них вызывает `private.assert_admin()`. Разрешение EXECUTE не означает право обычного пользователя создавать запись напрямую.

## 6. Перезапустите и проверьте локально

После шагов 2–5 остановите старый Vite через Ctrl+C и выполните:

```powershell
npm.cmd run dev
```

Откройте `http://127.0.0.1:5173/`. Если Vite выбрал другой порт, сначала освободите 5173 или согласованно измените BOOKING_ALLOWED_ORIGINS.

Проверьте на одном тестовом визите, не трогая существующих клиентов:

1. В приватном окне создайте запись после Turnstile. Проверьте, что сохранился один визит, и сохраните его персональный код.
2. В другой вкладке откройте этот визит по коду, перенесите, затем отмените. Проверьте освобождение времени.
3. Войдите администратором. Создайте запись по телефону, перенесите, измените статус и отмените. CAPTCHA для назначенного администратора не нужна.
4. Проверьте, что посетитель без решения Turnstile не может отправить форму.
5. Не проводите массовый нагрузочный тест на рабочей базе. Проверки превышения квот и прямого RPC выполняются автоматическими тестами на одноразовой базе.
6. В Cloudflare **Turnstile → ваш виджет → Analytics** проверьте успешные серверные валидации. В Supabase смотрите статусы вызовов без включения логирования тел запросов, заголовков авторизации или кодов управления.

Новый код сайта остаётся локальным. Размещение frontend для клиентов — отдельное действие; в этой задаче оно не выполнялось.

## Лимиты и хранение

Счётчики находятся в `private.booking_rate_buckets`, закрыты RLS и SQL-правами. Все экземпляры функции используют одну базу. Атомарное увеличение и транзакционная блокировка предотвращают гонки счётчиков. Квота расходуется в **отдельной завершённой транзакции до проверки CAPTCHA и записи**, поэтому ошибки и откаты не возвращают попытки.

| Операция | Общий лимит | Дополнительный лимит |
| --- | --- | --- |
| Все запросы функции вместе | 600/мин | — |
| Создание | 30/мин и 100/час | На телефон: 3 попытки/час и 10/сутки |
| Чтение по персональному коду | 300/мин | На запись: 30/мин и 180/час |
| Перенос | 60/мин | На запись: 6/мин и 20/час |
| Отмена | 60/мин | На запись: 6/мин и 20/час |
| Список интервалов / ближайший интервал | По 300/мин на операцию | Учитывается общий лимит |

Это лимиты **попыток**, включая ошибки и повтор после потери ответа. Для телефона используется нормализованный формат +996 и SHA-256 в ключе счётчика; код управления не сохраняется в счётчиках. Для операций с записью ключ привязан к её UUID, независимо от того, какой код прислал клиент. При превышении сервер возвращает HTTP 429 с Retry-After. Интерфейс просит подождать и не повторяет команду бесконечно.

Окна фиксированные, выровнены по серверному Unix-времени. На границе двух окон возможен краткий удвоенный всплеск; часовые квоты ограничивают длительное превышение. Истёкшие счётчики удаляются при следующем обращении. После изменения лимитов их следует снова проверить на тестовой базе; уже применённую миграцию не редактируйте — используйте следующую.

## Ограничения защиты

- IP-заголовки полностью игнорируются. Здесь нет проверенной цепочки доверенных прокси, поэтому X-Forwarded-For, X-Real-IP и CF-Connecting-IP не могут давать обход или определять идентичность посетителя.
- Общая квота может быть исчерпана атакующим и временно закрыть публичную запись всем. Лимит телефона также не подтверждает владение номером. Смена номера/UUID не обходит общий предел, но распределённую атаку это полностью не устраняет.
- PostgreSQL ограничивает выполнение бизнес-операций, но не отменяет стоимость уже пришедшего HTTP-запроса к Edge Function. Для защиты от DDoS/большого транспортного потока нужна отдельная защита на входе платформы. Один лишь Cloudflare-прокси перед сайтом не закрывает прямой адрес Supabase Function.
- Каталог без личных данных остаётся публичным. Авторизованные администраторы не ограничиваются гостевыми квотами; защищайте их аккаунты. Общие ограничения Supabase Auth не заменяются этой функцией.
- Turnstile снижает автоматизированный спам, но не гарантирует отсутствие людей-ботов или платного решения CAPTCHA. Подтверждение телефона, депозит и проверка подозрительных записей остаются отдельными мерами.
- При недоступности PostgreSQL или Siteverify создание закрывается. Сбой счётчиков закрывает все операции функции. Код управления остаётся секретом: его владелец может управлять соответствующей записью.
- Логи приложения и ошибки функции не содержат клиентов, токенов и SQL details. Не включайте у внешних сборщиков логов запись тел запросов и авторизационных заголовков.
- Автотесты не обращаются к настоящему Cloudflare и вашему рабочему Supabase. После развёртывания обязательно выполните ручную проверку выше.

## Автотесты

```powershell
npm.cmd test
npm.cmd run build
npm.cmd run test:cloud
npm.cmd run test:e2e
npx.cmd --yes --package=deno deno check supabase/functions/booking-gateway/index.ts
```

SQL/RLS и счётчики исполняются в PGlite, HTTP-обработчик функции — тот же, что развёртывается. Только ответы Cloudflare и Auth заменены тестовыми. В production-коде нет переключателя отключения CAPTCHA.

Для гонок нескольких настоящих соединений PostgreSQL обновлён `npm.cmd run test:db:live`: **только пустая одноразовая база** и явный флаг AURA_ALLOW_DISPOSABLE_DB_TEST=yes. Он не запускался против вашей базы. Подробности и выполненные проверки — в [CHECKS.md](CHECKS.md).
