# Управление фотографиями

Реализация подготовлена локально. Эти действия **не выполнялись** в подключённом Supabase.

## Что меняется на сайте

- **Админ-панель → Контент сайта**: главное фото, логотип, фотографии в существующем блоке «О салоне», портфолио (фото, альтернативный текст, подпись, категория, порядок, видимость и удаление).
- **Мастера → Редактировать**: загрузка портрета и альтернативный текст в существующей форме. Этот же портрет используется в карточке мастера, ближайших окошках и выборе мастера при записи. Дублирующей настройки в «Контенте сайта» нет.
- В «О салоне» несколько фотографий переключаются кнопками, новый раздел не добавляется. Порядок в редакторе меняется перетаскиванием или кнопками «Выше»/«Ниже», доступными также с телефона и клавиатуры. Без загруженного логотипа сохраняется существующее текстовое название. Фото категорий услуг и служебное фото экрана входа остаются прежними.
- Существующие локальные картинки не удаляются. Новые записи метаданных начинают с тех же путей; портреты существующих мастеров сохраняются. Если изображение явно убрано или не загрузилось, показывается нейтральная заглушка. SVG-заглушка встроена разработчиком: загрузка SVG пользователем запрещена.

Выбранный файл и обрезка сначала существуют только в памяти формы. Кнопка сохранения последовательно обрабатывает новые файлы, а затем одной транзакцией публикует метаданные. При частичном сбое готовые загрузки остаются в черновике для повторной попытки. Перезагрузка/выход из раздела не сохраняют черновик; подтверждение браузера предусмотрено для закрытия/перезагрузки страницы.

## Порядок установки

1. Проверьте, что уже применены миграции `001`–`005`, включая `202610270005_booking_protection.sql`. Нужны существующие `private.admin_users`, `private.assert_admin`, транзакции профилей и серверные квоты. Не запускайте `seed.sql` и `db reset` для рабочей базы.
2. В Dashboard → SQL Editor выполните **только** содержимое новой миграции [202610280006_site_media.sql](supabase/migrations/202610280006_site_media.sql). Она выполняется в транзакции. Старые миграции не редактировались; записи клиентов, услуги и профили не пересоздаются. Если применяете через Supabase CLI, сначала сверяйте `supabase migration list` и `supabase db push --dry-run`, чтобы вместе с ней не применить неизвестные изменения.
3. Миграция сама создаёт private bucket **`site-media`**, лимит хранимого объекта 5 МиБ, разрешённый MIME `image/webp`, таблицы метаданных и restrictive RLS-политики. Вручную делать bucket публичным или разрешать INSERT/UPDATE/DELETE для `authenticated` **не нужно**. Публичные изображения выдаёт Edge Function после проверки опубликованной ссылки.
4. Установите зависимости из lock-файла и подготовьте WASM:

   ```powershell
   npm.cmd ci
   node scripts/prepare-media.mjs
   ```

   Скрипт копирует WASM из закреплённого `@imagemagick/magick-wasm@0.0.44` в `supabase/functions/site-media/vendor/magick.wasm`. Папка `vendor` исключена из Git; перед каждым развёртыванием её нужно подготовить. Зависимости Edge Function закреплены отдельно в `deno.json`/`deno.lock` формата 4. Для проверки используйте приведённую ниже версию Deno, чтобы случайно не обновить lock-файл до формата 5.
5. В Supabase Dashboard → Edge Functions → Secrets добавьте **`SITE_MEDIA_ALLOWED_ORIGINS`** — точные адреса фронтенда через запятую, например `https://salon.example`, без завершающего `/`. Для локальной проверки — `http://localhost:5173,http://127.0.0.1:5173`. Это серверная переменная; в `.env.local`/`VITE_*` ничего нового не требуется. Пример добавлен в `supabase/functions/.env.example`. Существующие переменные Turnstile и `booking-gateway` не меняйте.
6. На машине с Docker и Supabase CLI, поддерживающим `static_files` (CLI 2.7.0 или новее), из корня проекта выполните вручную:

   ```powershell
   supabase functions deploy site-media --project-ref YOUR_PROJECT_REF
   ```

   Функция использует `SUPABASE_URL` и `SUPABASE_SERVICE_ROLE_KEY`, которые предоставляет серверное окружение Supabase. Не переносите service role в браузер. В `config.toml` для этой функции указано `verify_jwt = false`: GET доступен посетителям, но каждый пользовательский POST проверяет токен через **Auth getUser**, затем SQL `is_admin()`. Upload/finish дополнительно проверяют `private.admin_users` в service-only RPC. Значения `user_metadata`, роли и идентификаторы из тела запроса не определяют права.

   WASM включается как статический файл. Не используйте `--use-api` для такого развёртывания без проверки поддержки статических файлов вашей версией CLI. См. официальные инструкции [Supabase: WASM](https://supabase.com/docs/guides/functions/wasm) и [обработка изображений](https://supabase.com/docs/guides/functions/examples/image-manipulation).
7. Проверьте функцию на отдельном тестовом Supabase, затем соберите и разместите обновлённый фронтенд обычным способом. **Эта первичная установка требует новой сборки; последующие изменения фотографий — нет.** До установки новой медиа-миграции публичная страница продолжает использовать существующие картинки, а ошибки медиа не блокируют запись. Новое сохранение фотографии требует миграции и функции.

## Обработка и безопасность

- Исходник: JPEG/PNG/WebP, максимум **10 МиБ**, **6000 px** по каждой стороне и **12 500 000 пикселей** суммарно. Число прочитанных байтов ограничивается независимо от `Content-Length`. Размеры извлекаются из реального JPEG/PNG/WebP-заголовка до декодирования; MIME должен совпадать с содержимым.
- Сервер декодирует изображение ImageMagick WASM с принудительно выбранным разрешённым декодером; проверяет фактические размеры, применяет EXIF-ориентацию, обрезку, уменьшение до 2048 px по длинной стороне и повторное кодирование в WebP. EXIF/GPS/комментарии/профили удаляются. Прозрачность сохраняется, фон не подставляется. APNG/анимированный WebP, SVG, GIF, HEIC и исполняемые файлы не принимаются.
- Оригиналы в Storage не сохраняются. В bucket попадает только новое обработанное изображение с UUID-именем; перезапись существующего объекта отключена. Браузер не выбирает путь записи/удаления. Серверные RPC недоступны `anon` и `authenticated`, включая администраторов; обычные SQL-команды публикации проверяют назначение администратора.
- Новая ссылка публикуется только после успешной записи файла и перехода ассета в `ready`. Ошибки декодера/Storage/SQL оставляют старую ссылку. Профиль мастера и его фотография сохраняются в одной транзакции с исходными проверками расписания; клиентские записи не удаляются.
- У контента есть серверная ревизия, у фотографии мастера — отдельная версия. Устаревшая форма получает конфликт, а не перезаписывает новую фотографию. После конфликта сохраните нужный текст отдельно, нажмите «Загрузить актуальную версию»; для мастера закройте и откройте профиль заново. Автоматического слияния двух черновиков нет.
- Новые UUID дают новые URL, поэтому замена не зависит от старого кеша. Метаданные перечитываются после сохранения, при открытии/возврате на страницу и каждые 30 секунд в видимой вкладке. Изображения кешируются на час. Ранее просмотренное изображение может остаться в кеше посетителя после скрытия; публичная публикация не является средством отзыва уже скачанных копий. Черновикам выдаются только временные подписанные ссылки для администратора.

## Очистка незавершённых загрузок

После сохранений интерфейс запускает безопасную очистку, сбой которой не отменяет сохранение. Для очистки при отсутствии активности администратора настройте ежедневное выполнение на доверенном сервере/планировщике:

```text
node /ABSOLUTE_PROJECT_PATH/scripts/cleanup-site-media.mjs
```

В окружение **этого процесса** передайте `SUPABASE_URL` и `SUPABASE_SERVICE_ROLE_KEY` из хранилища секретов планировщика. Не добавляйте их в аргументы команды, Git или переменные Vite. Например, в системном cron с заранее настроенным безопасным окружением: `15 3 * * * /usr/bin/node /ABSOLUTE_PROJECT_PATH/scripts/cleanup-site-media.mjs`. Планировщик автоматически не создаётся.

Алгоритм:

1. Под общим с публикацией SQL-lock выбираются до 50 объектов старше 24 часов, на которые **не ссылается ни один** блок сайта, включая скрытые, и ни один мастер. Состояние `deleting` исключает повторную привязку даже при конкурентном сохранении.
2. Файлы удаляются через Storage API по путям из базы, затем удаляются метаданные. При ошибке Storage состояние сохраняется для следующей попытки. Прямая очистка `storage.objects` в production не используется.
3. Загрузка резервирует UUID до записи файла: прерванные загрузки известны сборщику. Недавно созданные незавершённые загрузки сохраняются 24 часа; старые фотографии удаляются после снятия всех привязок. Используемые файлы не удаляются независимо от их возраста. Скрипт обрабатывает максимум 1000 объектов за запуск; при большей очереди запустите повторно.

## Реально выполненные проверки и облачная приёмка

Итог от 29 октября 2026: 72 модульных/SQL-проверки, 8 браузерных сценариев серверного режима и 5 сценариев деморежима; TypeScript/сборка, Deno и синтаксис вспомогательных скриптов проверены. Полный отчёт: [CHECKS.md](CHECKS.md).

Локальные проверки выполняются командами:

```powershell
npm.cmd test
npm.cmd run test:e2e
npm.cmd run test:cloud
npm.cmd run build
npx.cmd --yes --package=deno@2.2.15 deno check --config supabase/functions/site-media/deno.json supabase/functions/site-media/index.ts
```

`test:cloud` — это **локальный** адаптер Supabase с PostgreSQL/PGlite, имитацией Auth и Storage и настоящими HTTP-обработчиком, декодером и SQL этой реализации. Он не подключается к облаку и не доказывает поведение облачного gateway/Storage CDN. Подробности покрытия — в `src/lib/siteMedia.test.ts` и `tests-cloud/site-media.spec.ts`.

Перед production на тестовом Supabase проверьте:

1. Назначенный администратор загружает JPEG/PNG/WebP, прозрачный PNG-логотип и портрет; крупный снимок телефона правильно ориентирован, EXIF/GPS отсутствуют в скачанном WebP.
2. POST без входа, обычный Auth-пользователь и поддельный токен не могут загрузить/очистить файлы. Обычный пользователь не получает доступ через Storage REST, даже если другая политика разрешает запись в другие buckets.
3. Поддельный JPEG, SVG под расширением PNG, файл свыше 10 МиБ, изображение свыше 6000 px/12,5 Мп и анимация отклоняются. Проверьте реальную скорость/память на максимальных размерах: Edge Functions имеют лимиты CPU/памяти; крупный сложный файл может потребовать уменьшения. Старая фотография в этом случае сохраняется.
4. Замените фото, прервите соединение до/после публикации и перезагрузите редактор: либо старая ссылка, либо успешно сохранённая новая, без потери рабочего изображения. Не повторяйте публикацию вслепую после неоднозначного сетевого сбоя — загрузите актуальную версию.
5. Два администратора редактируют одновременно: второй получает конфликт. Проверьте порядок, скрытие, удаление и отдельный браузер посетителя без входа.
6. Проверьте реальные iPhone/Android (в том числе выбор JPEG вместо HEIC), CORS на домене, развёртывание WASM, выдачу опубликованного файла без JWT, кеш и очистку старых бесхозных файлов с сохранением всех действующих привязок.
7. Повторите вход администратора и создание/перенос/отмену записи с настоящим Turnstile и действующими лимитами. Локальные тесты проходят через эмуляцию проверки CAPTCHA, а не обращаются к Cloudflare Siteverify.

Облачная база, Storage, секреты, Edge Functions и хостинг в рамках реализации не изменялись.
